# Canary 03 · Решение по дизайну резервирования

**Решение: визуальный дизайн не требуется** (`design.json`: `required: false`).

Обоснование:
- BRIEF прямо исключает UI («без UI; UAT не требуется»). Источник: `.agent/runtime/e31339c3-5930-41a1-bfc8-e9d16810e64e/context/5d011acd4c4ddbd6c52a4b3f0aa18cd2685920f27d94efbc51cdf46bae8b366a.json`.
- Задача меняет только JSON API (`GET /api/items`, новый `POST /api/reservations`) и хранилище SQLite. HTML-страница `/`, `labels.json` и `/health` остаются без изменений (SPEC C2), что проверяет AC11.
- Владелец в этой сессии выбрал сохранить формат `GET /api/items` (`quantity` = свободный остаток), поэтому новых экранов и полей для отображения нет.

Переиспользование (`design.json.reuse`):
- `app.py` — существующий `Handler` и `ThreadingHTTPServer` (через подкласс `InventoryServer` с увеличенной очередью); маршруты `/` и `/health` переносятся без изменений.
- `api.py` — существующий модуль бизнес-логики и контракт ответа `GET /api/items` (`id`, `name`, `quantity`).
- Стандартная библиотека Python (`sqlite3`, `http.server`, `json`, `unittest`) — без сторонних зависимостей.

Архитектурный дизайн (HTTP-контракт, схема, миграция, транзакции, восстановление, откат) полностью описан в `SPEC.md` (§3–§4, D1–D17) и `PLAN.md` (S1–S6). Отдельной стадии Design он не требует.
